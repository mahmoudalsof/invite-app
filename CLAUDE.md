# invite-app

A Saudi digital invitation and door check-in service for weddings and engagements (more event types later).
Hosts send invitations over WhatsApp, guests RSVP and get a QR pass on a web page (no install),
and a door team picked from the guest list scans passes at the venue, offline if needed.
The app name is not decided yet; "invite-app" is a working name.

Built solo by the owner (GitHub: mahmoudalsof) with AI help.

## Working rules

- **Ask before adding any technology.** Every library, tool, service or language feature that is not
  listed under "Approved stack" needs the owner's explicit approval first. Don't assume.
- Keep business logic on the server so the apps stay thin.
- The rules under "Product rules" are invariants: enforce them in the database or server, and test them.
- Arabic is the default language; everything also works in English. Guest pages and apps are right-to-left in Arabic.

## Approved stack

Server
- Go 1.27 (latest at time of writing), module `github.com/mahmoudalsof/invite-app/server`
- HTTP: standard library `net/http` router (method + path patterns), no framework
- Config: environment variables via `os.Getenv` into a config struct; logging with `log/slog`
- Database: PostgreSQL 18, driver pgx v5
- Queries: sqlc (pgx/v5 output) generated from `server/db/queries` against `server/db/migrations`
- Migrations: goose (SQL files with `-- +goose Up` / `-- +goose Down`), can run from inside the binary
- Background jobs: River (PostgreSQL-backed; no Redis)
- API: spec-first `api/openapi.yaml`; Go types and server interface generated with oapi-codegen for the stdlib router
- Web pages: `html/template` + htmx, self-hosted (htmx and fonts embedded in the binary; no CDNs, no Google Fonts calls)
- QR codes: yeqown/go-qrcode
- IDs: UUID v7 generated in Go with google/uuid (tables have no ID default)
- Sessions: opaque random tokens; only a SHA-256 hash is stored in Postgres; door links are short-lived
- Tests: standard library `testing` only (table-driven), against Postgres from Docker Compose
- Local dev: Docker Compose runs Postgres; the Go service runs on the host

iOS
- Swift + SwiftUI, minimum iOS 18
- Project generated with XcodeGen (`ios/project.yml`); do not commit hand-edited .xcodeproj changes
- API client generated by Apple's swift-openapi-generator from `api/openapi.yaml`

Android (after the iPhone launch, except door mode which ships with the iPhone beta)
- Kotlin + Jetpack Compose

Fonts: Amiri (display), IBM Plex Sans Arabic (UI), Aref Ruqaa (names on the card); English uses Cormorant Garamond and Inter.

Not yet approved (ask first): payment gateway (Moyasar, Tap or HyperPay), cloud provider (plan suggests Google Cloud Dammam),
error tracking, SMS provider, Apple/Google Wallet passes, any CSS framework, any Go library not listed above.

## Product rules (invariants)

- One invitation per adult guest; children travel free on their parent's invitation.
- An event is men only, women only, or both; each is a section with its own door and door team.
- The package is the TOTAL number of adult guests across all sections. Never exceed it.
  Enforced by the `guests_package_limit` trigger in migration 00001 (locks the event row; safe under concurrency).
- Nothing is sent to guests until the event is paid. After paying, the host can test, review and schedule
  ("later when ready", now, scheduled, or in stages).
- The event date is optional until sending; warn the host that it is required before invitations go out.
- Roles: host, co-host, section manager, inviter (with a quota), door. Door team members are picked from the
  guest list and join via a WhatsApp link; they only see scan and search for their own section.
- Women's names are private: in a women's section, hosts and the men's door team see counts, not names.
  Only the women's section manager and women's door team see names.
- Each guest has their own language (ar or en), which decides their messages and pages.
- A pass can be admitted only once: first admitted scan wins (partial unique index `check_ins_one_admit_idx`).
- The founder/staff never see guest lists or photos in normal operation.
- Prices are shown as final prices; the Saudi riyal symbol (U+20C1) goes after the number in Arabic, before it in English.

## Door check-in design

- The QR code holds no personal data: invitation ID, event, section, and an Ed25519 signature from the server.
- Door phones download their section's list before the event (stored encrypted, wiped 24 hours after the event),
  verify signatures offline, record scans locally and sync every few seconds when online.
- Scan answers: Welcome (admitted), Already used, Other entrance (wrong section), Not on the list (search or walk-in request to the host).

## WhatsApp

- Meta WhatsApp Cloud API directly (no reseller). Every outbound guest message is an approved template.
- Behind an interface with a fake implementation (records what would be sent) and a Cloud API implementation
  that can point at Meta's free test number during development.
- Keep message wording swappable: Meta may not approve templates built around a host's own long text.
- Sends go through River jobs, in paced waves; delivery statuses arrive on a webhook.

## Payments

- Behind an interface with a fake provider until the gateway is chosen.
- Packages are sold as an event service delivered outside the app (App Review Guideline 3.1.3(e)),
  with a fallback to in-app purchase if Apple disagrees.

## Build order

2. Host core on iPhone: create event, sections, add guests, preview card.
3. Sending: WhatsApp invitation to your own phone; guest page with RSVP and QR pass.
4. Door: iPhone door mode scanning passes, then offline mode; Android door mode.
5. Real payments, remaining screens, private beta, App Store; then the full Android app.
